# cortex-learn

What Cortex learns from agents' work. For now, the record of it: each normalized hook event becomes
the session, task and event rows the store keeps, each edit only the file watcher saw is given to
the session most likely to have made it, or to none, and what each open task did is kept until it
ends. It also tells what a shell command line ran: the checks of the runners it knows, the user's
own test commands, and git restores, what became of a task that has ended, what its work adds to the interest of each node it touched, the links it draws between the nodes it used together, and one record of what it did.

## What it must never do

- Keep a prompt's text (a task keeps the prompt's hash, and its first 200 characters only when
  `privacy.store_prompt_excerpt` is on), a command, a search pattern or anything a tool printed.
  The words that say why a task ended as it did name what a check vouched for, the runner and its
  exit code, never the command line, a path or code.
- Call a task a success without having seen a check pass on its work, or a revert without every
  file it edited being back as it was.
- Let a score or a weight stand for more than it was earned at: each is kept as of the task that
  earned it, and the decay of the tasks since is applied where it is read.
- Teach anything from a task that failed, was reverted or was left: links grow from work that was
  seen to hold up, and the files a reverted task changed together lose what they gained.
- Put a prompt, a command line, a path or code in a task's record: it holds node ids, counts, line
  numbers, exit codes and runners' names, and is trimmed until those fit the bound the store keeps.
- Write the store itself: it records inside a transaction the daemon's single writer opens.
- Take a check as passed when the command line's exit status does not vouch for it:
  `cargo test | tail` exits as `tail` does, so it tells nothing.
- Take a check as failed when the line's failure may be another command's: `cd x && cargo test`
  may have failed at the `cd`, so it tells nothing either.

| `Recorder::new`, `Recorder::record` | Records one event in a write transaction, the shell commands told by the `Commands` it is given. A prompt starts a task numbered across the repository, named by `cortex_core::task_id_of_prompt` and held out or not by `cortex_core::is_held_out` at the share the recorder is given (`holdout.share`), ending first any task its session left open when the end of the previous answer never arrived; the end of the answer or of the session ends it as `unknown`. A subagent is a session of its own with its parent's id, and its events belong to the parent's open task. A tool call is recorded after it ran, as a read, a search, an edit (one row per changed stretch of lines, up to `cortex_core::MAX_RANGES`), a shell command (with the runner and kind of the check its exit status vouches for, by `Commands`; the highest ranked when it ran several: tests, a build, a type check, a lint) or another tool, with the file's graph node when the file is indexed, and for a read that did not fail the short hash of what the index holds for the file; the moment before a tool runs is not kept. An event from a session the store has not seen registers the session. `record` returns the `TaskState` of the task the event ended, if any. After a transaction that was rolled back, `Recorder::forget_stored` drops what the recorder took the store to hold, the tasks' states included, which are rebuilt from the store; what it saw of sessions' work stays |
| `TaskState`, `Step`, `FileNode`, `RunCheck`, `MAX_TASK_ROWS`, `MAX_TASK_STATES`, `MAX_TASK_HIT_BYTES` | What a task did, kept as its rows are stored: each read, edit, search and shell command a step in the order recorded (a read, edit or search whose tool reported a failure left out), with when it happened, its file and graph node, its lines, the check of a shell command (its runner and kind) and its exit code. | `judge`, `reverted_after`, `Judgement`, `FileNow`, `TaskEnd` | What became of a task that has ended, from its state and what each file it edited holds at present, with the words that say why for `tasks.outcome_evidence`. | `interest_of`, `add_interest`, `EarnedInterest` | What a task's work adds to each node it touched, and the tier each score puts a node in. A score above 0.2 is interesting, at or below it fog |
| `tier_now` | The tier a stored interest row stands in at a later task: a landmark as the last task to choose the landmarks left it, else interesting while its score brought forward by `learning.interest_decay` stands above 0.2, else dark |
| `links_of`, `add_links`, `EarnedLinks`, `Linking` | The links a task's work draws between the nodes it used together, as undirected edges of the graph. | `episode_of` | One record of what a task did, for the archetypes that cluster tasks later: the files it read before its first change in the order it first read each, with how many times, at most 20; the files it changed in the order it first changed each, each with how many of its lines the changes covered (a line counted once) and the symbols those lines touched, each with whether a change covered the line its declaration starts on; the checks it ran in order with their runners and exit codes, a check that never finished among them; what went wrong (a runner whose check failed and later passed, the files it changed and put back itself, the stretches it read more than three times); and what became of it. | `label_injections`, `LABELLED_FILES` | What a task's end says of each injection its prompt got, a retrieval the gate kept back and a held-out task's among them: its label, 1 when the task used one of its first three files (edited it, or read it and edited a file that names it; a file it used only as it was given, without reading it, does not count), else 0, and its used count, how many of its files the task read or edited. | `Learner`, `Learned`, `MAX_SESSIONS_KEPT`, `cluster_tasks` | What a task's end teaches, in the one transaction `Learner::learn` is given: the judgement and its words, stored on the task's row; the interest its work earned; the links between what it used together; the labels of the injections its prompt got, then the self-check when one of them reached the agent; and its record. | `archetypes_of`, `MAX_CLUSTERED_TASKS` | The clusters the newest task records fall into, at most 2,000 of them read, which retrieval matches a prompt against. The clusters covering the most tasks are kept, then those worked in most recently, at most 256 |
| `Commands::new`, `Commands::recognise`, `Commands::tell`, `Told`, `Ran`, `Check`, `Restore`, `CONFIGURED`, `PatternError` | What a shell command line ran, from the folder it ran in, in the order of the line, as far as its exit status vouches: each command told ended its pipeline, sits in the line's last and-or list, ran whenever what came before it there succeeded, and is followed by `&&` alone, neither inverted by `!` nor run in the background, so that when the line exits 0 each of them ran and exited 0; and the check a line that exits otherwise is the failure of, if any: the one ending the last pipeline of the last and-or list, that pipeline alone in it or after `||`, neither inverted nor in the background. ## Tests

```sh
cargo test -p cortex-learn
```

The tests record event sequences in the orders Claude Code sends them (a whole task, `/compact`,
`/clear`, a subagent, a lost Stop, an unknown session) into a real store and compare every row
with rows written by hand. The watcher's edits are tested the same way: how long each is held,
when a hook's edit claims it (a failed one does not), and which session gets it at the edges of the
30 s window, after a session ends, for a subagent and on a tie. One test searches the database's
files for marker words placed in a prompt, a command and a search pattern. The command lines of
every runner, what the exit status vouches for, git restores and their paths are tables of real
lines with the answers written by hand; two properties check that any text reads twice the same
without a panic, and that what follows a line built from known commands decides what it vouches
for. The task states are compared with steps written by hand: a task's reads, edits, searches and
shell commands with failed tools left out, files indexed after their event given their nodes at
the end, a state rebuilt after a restart, after a rolled-back batch and from a row that cannot be
read back, the cut at 4,096 rows for a task ended by its answer's end and by the next prompt, the
found files' bound, the state touched longest ago dropped for room, and what each edited file
held before the task: a hook's edit before the index saw the change and after it, an edit only
the watcher saw, a failed edit, a new file, the first content kept, and the contents left unknown
after an edit too close to another (a report already taken, a store not read since, a file never
read) and in a rebuilt state. What became of a task is a
table of tasks recorded one by one with the outcome and the words written out by hand for each: a
check that passed and one that failed after the last edit, a check before it and one between two
edits, a lint, a check that never finished, nothing run and nothing edited, every edited file back
and one of them left changed, contents the index does not read, a file created and gone again and
one deleted, a git restore of a file, of a folder, of everything, one before the edit, one that
failed and one that covered only part of the task, a revert part by contents and part by a
restore, a content read before the edit and after it, a check a restore followed and one followed
by a restore of a file the task never edited, a revert outranking a passing check, a task left by
the next prompt and by its session's end, a state that shows only part of the task, a state rebuilt from rows after a passing check and a restore, which no check vouches for, and one whose rebuilt restore came before a later edit and passing check, and a revert
the next task shows, including one its steps do not show. The interest a task earns is one worked
example of every increment at once, with the symbols of a file given lines of their own and the
sums written out by hand, and then: work that vouches for nothing (a failed check, a lint, a read
of a file the store does not hold), what decay leaves of a score two tasks later, the landmarks a
repository of seven files allows, ties going to the smaller node, a file pushed out of the
landmarks, and a landmark that fades into the fog as the tasks go by. How many landmarks a
repository's size allows and where the fog ends are tables of their own, as is what decay leaves of
a weight, with a property that decay only ever takes from one. The links a task draws are worked
examples too: a successful task's six pairs across two levels with the three roles in the numbers,
what each outcome teaches, a reverted task weakening only the files it edited together, a weight
added to what decay leaves and held at its ceiling and at nothing, a pair with nothing to lose left
unwritten, and a task of 45 files keeping the 40 that mattered most; a property draws and weakens
one link over many tasks to watch its weight stay within bounds. The labels are worked out by hand
for seven tasks, each recorded as the daemon records it, an injection for its prompt in between,
and learnt from: a file edited among the first three, a file read and then used, files only read,
a used file past the first three, nothing touched, a retrieval the gate kept back, a held-out
task's, and a file used only as it was given; a session's primer is never labelled, and a task
with no injection writes none. The self-check's rule is worked out on label sequences by hand (a window not reached, a raise at 59 of 100, none again too soon, the floor itself, the most steps, the bar never lowered), and through a task's end: the hundredth unused delivered work order raises the bar, a work order the gate kept back does not run it. What a work order gives is worked out by hand too: the interest its
spans earn once read or edited (and none after a work order kept back or held out), and the links
a file and a symbol given gain once an edited node names them (and none after one kept back). The record of a task is one worked
example of fourteen steps with every part written out by hand, and then: a stretch read four times
against one read three times, a task of 300 changed files trimmed until it fits with its places
kept, and a task whose prompt, command and search pattern each carry a word of their own, none of
which is anywhere in its record. The clusters are a worked example of eight tasks with
the clusters, their files and their words written out by hand, one task among them that a
drifting cluster would have taken and words every task gives falling behind, and then: a task
that clears the bar with two clusters and joins the one it is more like, a tie going to the
older, only the tasks whose work stood clustered, the words of a function a task touched, a word
counted once for each task that gives it, a word too long to name anything left out, the newest
records read and no more than 2,000 of them, the bounds on a cluster's files and words, the
clusters kept when there are too many, and a repository with no records. What a task's end teaches
is worked examples too: a task that passed its tests, with its judgement, interest, link, record
and cluster written out by hand; tasks that failed or were left, which link nothing; a revert the
index shows only after the task's end, found at the session's next task's end; a success the next
task restores with git, which loses what it gave its links at both levels, decayed, and a
reverted task's share, while another session's share of the same links stays; a task whose work stood, left alone; a new file the index has not seen, not taken as
gone; a task reverted at its own end, not weakened again; and the sessions kept, a long task that
started first and ended last among them.
