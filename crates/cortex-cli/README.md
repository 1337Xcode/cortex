# cortex-cli

Builds the `cortex` binary: every command a user types and, as the other crates land, the internal
entry points agents and the daemon call.

## What it must never do

- Hold product logic. A command parses its arguments, calls the crate that owns the behaviour and
  prints the result.
- Print command output anywhere but through `src/output.rs`, which escapes control characters so
  that a path or another program's answer cannot drive the terminal, or panic on a closed pipe. Help,
  `--version` and usage errors are printed by clap.
- Let `cortex hook` print or exit with anything but 0: an agent may block its own tool call on a
  hook's exit code or show its output to the model. `hook` is handed to `cortex-hook` before
  clap sees the command line.

## Entry points

Without `--root`, `status`, `doctor`, `receipts`, `where`, `config` and `features` work on the
repository the current folder is in, found as a hook finds it (the nearest folder at or above it
that holds `.cortex`, never the home folder, or a linked working tree's main working tree that
holds one), and otherwise on the current folder; `init` starts from the current folder. In a
linked working tree, the paths `note`, `claims` and `why` are given are read from the linked
working tree's top, and `where` and `why` show and check that working tree's own files, as its
agents' prompts do.

| Command | What it does |
| --- | --- |
| `cortex version`, `cortex --version` | Prints `cortex <version>` |
| `cortex daemon [--root <folder>]` | Keeps the repository's index, the current folder's when no root is given, as its only writer: indexes what changed since the last index, then watches the repository and indexes again after each change. Which files count follows the ignore files, the user's global gitignore among them, which it asks git for (`core.excludesFile` in the user's configuration, else the system's, never the repository's own); when git cannot answer it says so and reads none. In huge mode it parses the files it took inventory of, the changed ones first, `index.crawl_files_per_second` a second on one thread. Once the first index is done it mines the git history in the background for which files change together, and the commits HEAD gains after. Writes `cortex: daemon ready: ...` on stderr after the first index and stops after `daemon.idle_shutdown_minutes` without a request or a change once nothing waits to be parsed. A second daemon on the same repository is refused. Each start records the repository as set up on this machine in `~/.cortex/repositories/<id>`, which hooks look for before they serve it. With `--adopt`, which a hook passes once adoption is on, it first takes the folder's set-up lock (`~/.cortex/run/<id>.adopt`, kept while it runs; a second start finds it taken and ends, writing nothing), then checks again, with the whole configuration, that Cortex may set the folder up on its own: a git working tree's top below the home folder, not the user's own Cortex folder, not the temporary folder, inside it or holding it, no `.cortex/off` at or above it, no `adopt.exclude` pattern matching it or a folder above it, the top of its working tree as git says, and in a linked working tree the same of its main tree. A folder already set up here is served as it is. Otherwise it sets the repository up as `cortex init --yes` does, with no agent's hooks, its ignore lines in the exclude file git keeps for it (never a `.gitignore`), all or nothing (when a write fails, every file gets back what it held and what was made is removed), and runs; the first session start or prompt of an agent that shows its user hook messages then tells the user, never the model, "Cortex set up this repository for your agents; `cortex off` turns it off here." A folder a rule refuses is remembered with why in `~/.cortex/run/refused/` (the newest 256), so that hooks stop offering it, and nothing is written in it; a set-up that fails (a configuration that cannot be read, git missing) is written to `~/.cortex/logs/adopt.log` and not remembered |
| `cortex hook --agent <agent> --event <event>` | What an agent's hook configuration runs. Reads the payload on stdin (at most 1 MiB, read to the end of its JSON object, which must come within a third of the event's hard timeout), turns it into an event, and hands it to the repository's daemon before the event's deadline; when no daemon runs, it starts one in the background, detached, and returns at once. The repository is the nearest folder at or above the payload's working folder that holds `.cortex`, never the home folder or above it; outside one, nothing happens. At a session's start and at a prompt it asks the daemon for the primer or the work order with the event, and prints it as the agent's hook JSON (`hookSpecificOutput.additionalContext`, for Claude Code and Codex alike) when the whole answer came before the event's deadline; at every other hook, and whatever goes wrong, it prints nothing. It always exits 0; failures go to `~/.cortex/logs/hook.log`, at most one line a second, without payload text. It is read before the rest of the command line, so no argument makes it print or fail. Run with no arguments at all while its standard input is not a terminal, as an agent that imports Claude Code's settings may run Cortex's Claude Code hook without its argument list, `cortex` prints nothing and exits 0; and Cortex's Claude Code hook passes over a payload carrying a field only Cursor, GitHub Copilot or TRAE sends (`cursor_version`, `conversation_id`, `generation_id`, `workspace_roots`, `llm_tool_name`, `loop_count`, `timestamp`), which that agent's own hooks record |

## Tests

```sh
cargo test -p cortex-cli
cargo bench -p cortex-cli --bench hooks
```

The tests in `tests/` run the built binary. The daemon tests start it on temporary repositories
with an empty home folder, so the user's own configuration never applies.

The `hooks` benchmark runs the built `cortex hook` once per sample, 100 samples per event, from
the process's start to its exit: SessionStart, UserPromptSubmit, PreToolUse on a read, PostToolUse
on an edit and Stop, each on a recorded Claude Code payload against a daemon on a temporary
repository of 10,000 generated source files committed to git, once its graph is built, and a hook
given no input, which ends before it asks the daemon anything. Before measuring, it checks that the
session's start prints its primer and the prompt, which names a function and a class the files
import, prints a work order, and that a one-word prompt prints nothing, which is timed too; that
an edit changing a function's header is told of its callers; and
that a read of the file the session read whole is told so. It also times the session's start after
a compaction, each sample after a compaction of its own, checked to print its recap. Then it times the prompt's retrieval alone, asked of the daemon
directly with no hook process to start, each request from a session of its own and checked to get
a work order. Then it runs the five events again from a repository whose daemon is down and cannot
come up (the benchmark holds its run lock, as a daemon still starting does), so that each sample is
a hook that finds no daemon, starts one and exits. It fails when a hook fails or prints nothing
where it should answer, when a retrieval gives no work order, when the daemon did not handle each
event's requests, or when a hook with the daemon down started none.

Before those, it times the prompt and the edit again with `history.why`, `history.seeds` and
`history.experience` on, on the same 10,000 files with a scripted year of history: 300 commits a
day apart, five files each, change 500 of the Python files three times, and two commits in three
give a reason and fix an issue. A session reads 200 of those files, upkeep runs until it has
warmed its day's 200 and the history worker has blamed them and carded their commits, and three
tasks leave their records. With the daemon stopped, it measures the pages SQLite's `dbstat` gives
the history tables (`blame_cache`, `change_cards` and `commit_terms`, their indexes included)
against every file in `.cortex/`, prints each share, and fails when together they take 2% or
more. Then each sample is a session of its own: its prompt, checked to carry a why-line, the
prompts leaving the number of blames kept as it was; and an edit of a function's header, its task
opened by a start and a prompt first, checked to be told the commit the line came from.

Configuration comes from `~/.cortex/config.toml`, then the repository's `.cortex/config.toml`; a
file over 1 MiB is refused, and an unknown key prints a warning.

The `profile` key sets the feature switches' defaults before any other key, so every key a file
sets overrides it:

| Profile | What it sets |
| --- | --- |
| `standard` (the default) | Nothing: every key keeps its documented default |
| `lean` | `hints.runtime_grounding`, `hints.narrow_tests`, `hints.redundant_commands`, `compaction.keep_list`, `coordination.contracts`, `history.why`, `history.seeds` and `history.experience` to `false`, leaving work orders and warnings. Each is off by default now, so `lean` gives what `standard` gives until one of those defaults turns on |
| `everything` | The same eight keys to `true` |

No profile changes `strict_mode` or `privacy.store_prompt_excerpt`: holding an agent's stop and
keeping prompt text are the user's own choices.
