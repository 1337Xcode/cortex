# cortex-cli

Builds the `cortex` binary: every command a user types and, as the other crates land, the internal
entry points agents and the daemon call.

## What it must never do

- Hold product logic. A command parses its arguments, calls the crate that owns the behaviour and
  prints the result.
- Print command output anywhere but through `src/output.rs`, which escapes control characters so
  that a path or another program's answer cannot drive the terminal, or panic on a closed pipe. Help,
  `--version` and usage errors are printed by clap.
- Let `cortex hook` print or exit with anything but 0: an agent may block its own tool call on a
  hook's exit code or show its output to the model. `hook` is handed to `cortex-hook` before
  clap sees the command line.

## Entry points

Without `--root`, `status`, `doctor`, `receipts` and `where` work on the repository the current folder is in, found as
a hook finds it (the nearest folder at or above it that holds `.cortex`, never the home folder, or
a linked working tree's main working tree that holds one), and otherwise on the current folder;
`init` starts from the current folder. In a linked working tree, the paths `note`, `claims` and
`why` are given are read from the linked working tree's top, and `where` and `why` show and check
that working tree's own files, as its agents' prompts do.

| Command | What it does |
| --- | --- |
| `cortex version`, `cortex --version` | Prints `cortex <version>` |
| `cortex daemon [--root <folder>]` | Keeps the repository's index, the current folder's when no root is given, as its only writer: indexes what changed since the last index, then watches the repository and indexes again after each change. Which files count follows the ignore files, the user's global gitignore among them, which it asks git for (`core.excludesFile` in the user's configuration, else the system's, never the repository's own); when git cannot answer it says so and reads none. In huge mode it parses the files it took inventory of, the changed ones first, `index.crawl_files_per_second` a second on one thread. Once the first index is done it mines the git history in the background for which files change together, and the commits HEAD gains after. Writes `cortex: daemon ready: ...` on stderr after the first index and stops after `daemon.idle_shutdown_minutes` without a request or a change once nothing waits to be parsed. A second daemon on the same repository is refused |
| `cortex hook --agent <agent> --event <event>` | What an agent's hook configuration runs. Reads the payload on stdin (at most 1 MiB, read to the end of its JSON object, which must come within a third of the event's hard timeout), turns it into an event, and hands it to the repository's daemon before the event's deadline; when no daemon runs, it starts one in the background, detached, and returns at once. The repository is the nearest folder at or above the payload's working folder that holds `.cortex`, never the home folder or above it; outside one, nothing happens. At a session's start and at a prompt it asks the daemon for the primer or the work order with the event, and prints it as the agent's hook JSON (`hookSpecificOutput.additionalContext`, for Claude Code and Codex alike) when the whole answer came before the event's deadline; at every other hook, and whatever goes wrong, it prints nothing. It always exits 0; failures go to `~/.cortex/logs/hook.log`, at most one line a second, without payload text. It is read before the rest of the command line, so no argument makes it print or fail |
| `cortex status [--root <folder>]` | Asks the repository's daemon for its process, version, uptime and queue (what waits, and any events dropped, batches not recorded or checkpoints of the store's log that failed), how long the daemon itself took to handle each hook (the median, 95th and 99th percentiles of each hook's last 1,000 requests, in milliseconds, from the first byte of a request to its answer being ready: the hook's own process and connection are not counted), its latest errors (the last 10, each with how long ago it last happened and how many times) and what its co-change miner is doing (waiting for the first index, no repository at the root, mining, ready, or failed and tried again later, with why, and that the `git` program reads the history when `gix` cannot; or that the daemon does not say), what the daemon read of the work tree (how many uncommitted files are kept to seed retrievals, of how many git listed when fewer, as of how many looks, and the failed ones; or that no git program is on the `PATH`, that no repository is at the root, that the repository's own git configuration names a filter a look would run, that the repository is a partial clone and git, older than 2.45, could fetch in it, that more files changed than a look takes in, that HEAD moved and it is looking again, that the latest look failed, or that it has not looked yet) and what its graph holds (its nodes and links, whether co-change links are in it, how many times it was built and how long the latest build took, and how many builds failed, or that none is built yet) and what its last run of upkeep removed and whether it finished (or that none ran since it started), or says it is not running, not answering or speaks another protocol. A daemon of an older Cortex is first replaced: asked to stop, waited for until it lets go of the repository, and a daemon of this build started in its place (a newer daemon is left alone); then prints whether the first index has finished, the scale mode the last index recorded (and the one the configuration pins, if any), how many files are stored, parsed and waiting to be parsed, and how far the git history is mined (how many commits, up to which, and how long ago the last full mining was), what the gate asks before it hands a work order over (before a confidence model is kept, its bar for the prompt's words, 0.50 when 2 kinds of evidence agree and 0.10 when 3 do, raised by the self-check; once one is kept, which model, how many labelled retrievals it was fitted on and its AUC on later ones, and the chance it must give, `retrieval.min_confidence` or at least 0.85 in small mode, raised by the self-check to at most 0.90; and, when the newest model kept cannot be used by this build, that the bars decide until upkeep fits another) and what the self-check last found (the precision over the latest work orders given, and how many steps of 0.05, at most 4, it raised the bar, and when), the warnings given (how many files they named, and of those marked at their task's end how many were then read or edited, with the share), how many files the lines naming what earlier tasks read next named and how many of those were then read or edited, once one was counted, and, only when some fact needs a person, how many facts are anchored to code the index no longer holds and how many are suspect since their code changed, which `cortex facts` lists; or that the repository has no index. Only reads the store For each linked working tree an agent worked in since the daemon started, a line names its top and says what the daemon read of its uncommitted changes, as for the work tree |
| `cortex init [--root <folder>] [--scope <scope>] [--yes]` | Sets Cortex up in a repository: the top of the git repository that holds the folder it starts from, as `git rev-parse --show-toplevel` says (git found on the `PATH` outside every repository around the folder), and prints which; that folder alone, with a note saying why, when git is not on the `PATH`, names no repository, names a top that does not hold the folder (a repository's `core.worktree` can name any folder), or names the home folder or a folder holding it. It never sets up the home folder itself or a folder holding it, whose `.cortex` is the user's own. It sets up the agents `--agents` names, or else every agent it finds on this machine (by its folder in the home folder or its program on the `PATH`), Claude Code as any other; with none found it writes no hook and says how to add one. An agent named twice is set up once. A found agent whose settings it cannot use (not the JSON the agent reads, or read-only) is left out with a note naming `--agents`, and the others are set up; a named one stops init. It does not make Droid's `~/.factory/hooks.json` while `~/.factory/settings.json` holds hooks, which Droid reads only while that file is absent. When Claude Code is among them it asks Claude Code its version as `doctor` does and refuses when it is older than 2.1.295. Then it asks two questions, once: measure Cortex's effect by leaving one task in ten without its help (yes by default, kept as `holdout.share` in the repository's `.cortex/config.toml`, or taken from the user's own configuration when set there); share facts with the team through a committed `.cortex/shared/` (no by default; kept in the `.gitignore`, so a team that shares has answered it; not asked outside git). It never writes the user's own `~/.cortex/config.toml`. A question answered there is not asked again. `--yes` takes the defaults; otherwise questions are asked on stderr and answered in a terminal, and without a terminal init refuses, naming the question. Every file it may change is found, read and checked before it asks, and nothing is written until every question is answered. In a git repository it appends to the `.gitignore`, first, what git does not ignore yet: `.cortex/` (or `.cortex/*` and `!.cortex/shared/` when the team shares), and `.claude/settings.local.json` when init makes that file. It registers Cortex's hooks with Claude Code: in the repository's `.claude/settings.local.json` (scope `project`, the default), or in `~/.claude/settings.json` (scope `user`, which sets up the repository all the same). Each event Cortex records gets one exec-form hook: this binary run with `hook --agent claude --event <event>`, the event's tool matcher, its hard timeout in whole seconds rounded up, and `onFailure: "continue"`. Cortex's own hooks, found by a command named `cortex` whose arguments begin `hook --agent claude`, are replaced where the first of them was; the user's hooks and keys stay, in their order. Answers are appended to their configuration under their own table, never rewriting it. Each file is copied as it was read to a backup folder of the run's own, `.cortex/backups/<UTC milliseconds>-<process>/` in the repository (`~/.cortex/backups/` for the user's files), with a manifest naming the repository and, for each file, its kind, its copy and the copy's BLAKE3 hash, and the BLAKE3 hash of what it wrote; the manifest of the repository's files is also kept in the run's folder of the same name in `~/.cortex/backups/`, outside the repository, since a manifest inside one may have come with the clone (it is the copy `cortex uninstall` reads), and init stops before it changes a file when it cannot write it there; then a new file is written beside the old one, made for this write and never through a link, and renamed over the old one only if the old one still holds what was read. A file that holds more than 1 MiB, is not UTF-8 (or, for settings, not JSON), is read-only or is a link to nothing is refused and left as it is, and so is a `.gitignore` that is a link (git reads none through one) and a repository whose `.claude` or `.cortex` folder is a link or junction. Then it finds the repository's daemon or starts one (replacing one of an older Cortex; one of a newer Cortex that speaks another protocol is left alone and not waited for), waits until the daemon says its first index is done, for at most 5 minutes, saying on stderr every 2 seconds, while the store can be read, how many files it holds, prints the index's state as `cortex status` does, and runs `cortex doctor`'s checks, whose failures it reports without failing. A daemon that cannot be started or stops before its first index is done fails init, which names the daemon's log; the files are written by then, and running init again is safe. On Windows the daemon it starts holds none of init's handles, so a pipe reading init's output ends with init. Running it again writes nothing new In a linked working tree (`git worktree add`) of a repository with a main working tree, the repository it sets up is the main tree, which it names, with a note naming the linked working tree: the agents' hooks go to the linked working tree's own files, no `.cortex` is made there, even before the main tree is set up, and the ignore lines go to the exclude file `git rev-parse --git-path info/exclude` names, which git reads for every working tree of the repository, never to a `.gitignore`, which belongs to a branch; the run's manifest names the linked working tree, so that `cortex uninstall` restores its files too |
| `cortex doctor [--root <folder>]` | Checks, one line each, whether Claude Code will run Cortex's hooks for the repository and the daemon will answer them in time: the hooks are in exactly one settings file of the repository's or the user's and are what this build writes; no settings file it can read (the managed ones, the repository's local and shared ones, the user's) turns hooks off, by `disableAllHooks` as the most precedent file setting it says, or by a managed `allowManagedHooksOnly`; the hooks run this binary (it never runs a program a settings file names); Claude Code, asked `claude --version` (the program on the `PATH` as a shell finds it, never one inside the repository, for at most 5 s), is at least 2.1.295, the oldest the hooks work with (any later one passes, as Cortex ignores what a newer version adds to its hooks; one not found, as when it runs from an editor, is not checked); the repository's daemon answers and runs this build; and, while it does, 20 probes of each hook with a budget (SessionStart 120 ms, UserPromptSubmit 150 ms, PreToolUse on a read 40 ms, PostToolUse on an edit 80 ms, Stop 60 ms), this binary run as Claude Code runs it on payloads marked as probes, all reach the daemon, which answers and counts them and records none, and each hook's 95th percentile from start to exit is within its budget. Each failure prints its fix, and the command fails when any check did. Doctor writes nothing and starts or stops no daemon, and neither does a probe |
| `cortex receipts [--root <folder>] [--session <id>] [--days <n>] [--json]` | Shows what each task of the sessions started in the last `n` days (7 when not given), or of one session, took: its turns, tool calls, input tokens (uncached, read from the cache and written to it), output tokens and estimated cost, the tokens Cortex injected into it (only what reached the agent), the tokens of the session's primers, the work outside any task and each session's total with every token Cortex injected into it and, when its agent's transcripts do not record compaction calls (Claude Code's), how many compactions that total leaves out, with a subagent's work counted in the session that started it (a subagent's id is refused). Each metered session with responses then shows its prompt cache: the share of its input read from the cache, the share of its estimated cost spent writing to it when every response has a price, and how often its conversations lost the cache, counted by cause (a model switch, a compaction, idling past the cache's lifetime, text Cortex gave between the two responses), the losses with no known cause listed by turn and time, at most five (`cache_breaks` in the JSON, and `cache_write_picodollars` in each estimate). A task with no response recorded says so instead of showing zeros, a session of an agent whose transcripts Cortex does not read (Codex, for now) shows its tool calls and what Cortex gave it, and a repository with no store says nothing is recorded. Costs come from `~/.cortex/pricing.toml`, written from the price table this build ships the first time and read from then on, so edits to it win; it states the date its prices were read, and a response it cannot price gets no estimate and says why. It says whether enough of the repository's tasks were held out from Cortex to compare them with the rest and, once 30 tasks of each arm have ended, the comparison over every session the store holds: success rates, and, once each arm also holds 30 successful tasks whose usage was read, per successful task the median input and uncached input tokens, turns and tool calls, each difference with its 95% bootstrap interval (until then, how many such tasks each arm holds), and the injection precision: of the repository's work orders that reached the agent and were labelled at their task's end, the share that were used, or that none is labelled yet; and the warning precision: of the files the repository's warnings named and their tasks' ends marked, the share then read or edited (`warnings` in the JSON, its `used` the files followed up). `--json` prints the same as JSON, costs in picodollars. The store is only read |
| `cortex where "<question>" [--limit <1 to 5>] [--root <folder>]` | Asks the repository's daemon, started when none runs, what its retrieval engine finds for a question without the gate: the files (3 unless `--limit` says otherwise), each span's code as the file holds it, why each was found, and what the gate would have said, printed as the daemon writes it, with tabs kept and other control characters escaped. When the engine ran out of time it says so and names no file. With no answer it says whether the daemon has not built its graph yet or found nothing to show; a question the daemon could not answer is an error |
| `cortex consolidate [--root <folder>]` | Asks the repository's daemon, started when none runs, to run upkeep as soon as its writer is free instead of after a quiet spell; it answers at once, and `cortex status` then says what the run removed |
| `cortex export [--root <folder>]` | Writes the active facts to `.cortex/shared/facts.json` for a team that commits `.cortex/shared/`: each fact's text, kind and anchors (`path`, `path:symbol`, or `.` for the repository), no numbers, times or counts, sorted so that the same facts give the same bytes (`version` 1). The file is written through a new file renamed over the old one, never through a link; with nothing changed it is left as it is and said so. A fact import would refuse (about code that is gone, with more than 16 anchors, or a name too long) is left out and named, and past 1,000 facts the first 1,000 in the file's order are written |
| `cortex import [--root <folder>]` | Reads `.cortex/shared/facts.json` strictly and notes each fact as an import's: a candidate, never given to an agent until `cortex facts confirm` says it holds here; a fact already kept on the same anchors in like words is not added again, and one retired here stays retired and is named so. The file is read only when neither `.cortex` nor `.cortex/shared` is a link and it is a regular file of its own. A file that is not JSON, holds a field Cortex does not know, another version, more than 1,000 facts, a fact over 240 characters or with a control character, no anchor or more than 16, or an anchor that is not a repository path or holds an invisible character, or is over 1 MiB, is refused whole and nothing is imported; a fact whose file or symbol this clone does not have is skipped and named |
| `cortex claims list`, `cortex claims add <file>...`, `cortex claims release [<file>...]` (each with `[--root <folder>]`) | Advisory claims on files, which lock nothing: a claim tells the other sessions working in the repository that a session works on a file, so an edit of it by another is noticed to both while the claiming session is live. `add` claims the files (paths from the current folder, inside the repository) for the agent session at work, the one whose latest tool call came last within the 5 minutes before, so it is run from the agent's own shell; with none at work it is refused. A claim holds 2 hours (`coordination.claim_minutes`). `list` prints each claim: file, agent, the first 8 characters of the session id and how long ago it was made. `release` removes the claims on the files named, whoever holds them, or every claim; the repository's daemon, started when none runs, keeps them |
| `cortex why <target> [--root <folder>]` | Asks the repository's daemon, started when none runs, why code is where it is: the target is a file (a path from the current folder, inside the repository), that file and `:line` or `:symbol`, or a symbol's name. Prints, as the daemon writes it, the files its file is linked to by code, history and use and how strongly, the project facts about it true now, the sessions working on its file now and the warnings about it whose tasks have not ended; a target naming nothing or several things fails the command with the daemon's words |
| `cortex note "<text>" --at <path[:symbol]>... [--kind <kind>] [--root <folder>]` | Notes a project rule of the user's, active at once, about each file named (a path from the current folder, inside the repository) or a symbol it defines (after `:`, by qualified name, or by name when one alone has it), or about the whole repository when the anchor is its root folder (`.` from the root), alone, at most 10 such rules not retired. The repository's daemon, started when none runs, writes it and the command prints `fact <n> added`, or that a fact on the same files and symbols already says it (confirming it when it was a candidate or suspect); the user's note in other words than a fact alike on the same anchors corrects it. Run inside a coding agent's shell (Claude Code's `CLAUDE_CODE_CHILD_SESSION`, or Codex's `CODEX_THREAD_ID` or `CODEX_TOOL_CALL_ID` set), the note is the agent's: a candidate, which the command says waits for a person to confirm it. Refused, in words saying why: a path that is not a file, a file outside the repository or not indexed, a symbol the file does not define, more than 240 characters, a kind other than convention, decision, invariant, pitfall or ownership |
| `cortex facts list [--all]`, `cortex facts confirm <n>`, `cortex facts retire <n>`, `cortex facts edit <n> "<text>"` (each with `[--root <folder>]`) | Lists the facts that are active, candidates or suspect (retired ones too with `--all`), one line each: number, status, kind, text, what it is about (a name holding characters a terminal would act on printed as a placeholder saying so) and how often it was given to an agent; or carries the user's word on fact `n`: confirmed against the code as it is now (active), retired (never given again), or corrected (a new fact on the same files and symbols replaces it). A fact corrected since, a number no fact has, and a fact whose file is gone (for confirm and edit) are refused; so is any word on a fact from inside a coding agent's shell, where it would not be a person's. A note or a word on a fact reaches one daemon only: an older daemon that answered keeps its answer and is replaced after |
| `cortex uninstall [--root <folder>] [--scope <scope>] [--purge]` | Undoes what `cortex init` did to the repository, the current folder's when no root is given, and stops its daemon; with `--scope user`, also what init did to the user's own files, Claude Code's `~/.claude/settings.json` and `~/.cortex/config.toml`, which serve every repository, whatever repository each init set up. It reads init's manifests from the user's `~/.cortex/backups/` alone, those naming this repository, never one inside the repository, which may have come with the clone (the user's own files have their manifests there too). Run by run, newest first, and each run's changes last first: a file that holds what it held before that run is left alone; a file that still holds what init wrote gets back what it held before, from init's copy in `.cortex/backups/` once the copy's BLAKE3 hash matches the manifest's, or is removed when init made it, with the repository's `.claude` folder when that is left empty; a file changed since keeps the change, and only Cortex's hooks come out of Claude Code's settings and only the very lines init added after `# Cortex`, which the manifest records, out of the `.gitignore`, while Cortex's own `.cortex/config.toml` is kept as the user changed it. It reads and writes plain files only, never a link itself, and a repository's file only while its folder is still the repository's own; every write is made through a new file renamed over the old one, only while the file still holds what was read. Without `--scope user` the user's own files stay, and for each agent whose user file there holds Cortex's hooks, which run in every repository, uninstall says so in its last lines on stdout. A change that cannot be undone, such as one whose copy is gone or holds anything else, is named on stderr and its file left as it is, the others are undone all the same, and uninstall then fails. Then it asks the repository's daemon to stop, whatever its Cortex version (a daemon of another protocol reads a stop too), giving it 20 s from the first request to let go of the repository, and fails when a daemon that holds the repository has not answered by then. With `--purge`, once every change is undone and the daemon has stopped and no daemon holds the repository again (otherwise it deletes nothing and says why, so that the backups a retry needs stay), it deletes the repository's `.cortex/` but `.cortex/shared/`, which the team commits, `.cortex/config.toml` included whatever the user changed in it, then init's manifests for this repository and the daemon's log and the files it rotated to in `~/.cortex/`, leaving the run files; it deletes nothing through a link (a link inside `.cortex/` goes as a link), refuses a `.cortex` that is one, and refuses the home folder, whose `.cortex` is the user's own, and any folder holding it; a purge that fails partway says the steps it finished before the error; without it, a note says `.cortex/` stays, holding the index and init's backups. It says what it did only once all of that is done, so that an output closed early never stops it partway. Running it again changes nothing |

Adding a command means one new module in `src/commands/`, one variant of `Command` and one match
arm in `src/commands/mod.rs`.

## Tests

```sh
cargo test -p cortex-cli
cargo bench -p cortex-cli --bench hooks
```

The tests in `tests/` run the built binary. The daemon tests start it on temporary repositories
with an empty home folder, so the user's own configuration never applies.

The `hooks` benchmark runs the built `cortex hook` once per sample, 100 samples per event, from
the process's start to its exit: SessionStart, UserPromptSubmit, PreToolUse on a read, PostToolUse
on an edit and Stop, each on a recorded Claude Code payload against a daemon on a temporary
repository of 10,000 generated source files committed to git, once its graph is built, and a hook
given no input, which ends before it asks the daemon anything. Before measuring, it checks that the
session's start prints its primer and the prompt, which names a function and a class the files
import, prints a work order, and that a one-word prompt prints nothing, which is timed too; that
an edit changing a function's header is told of its callers; and
that a read of the file the session read whole is told so. It also times the session's start after
a compaction, each sample after a compaction of its own, checked to print its recap. Then it times the prompt's retrieval alone, asked of the daemon
directly with no hook process to start, each request from a session of its own and checked to get
a work order. Then it runs the five events again from a repository whose daemon is down and cannot
come up (the benchmark holds its run lock, as a daemon still starting does), so that each sample is
a hook that finds no daemon, starts one and exits. It fails when a hook fails or prints nothing
where it should answer, when a retrieval gives no work order, when the daemon did not handle each
event's requests, or when a hook with the daemon down started none.

Configuration comes from `~/.cortex/config.toml`, then the repository's `.cortex/config.toml`; a
file over 1 MiB is refused, and an unknown key prints a warning.
