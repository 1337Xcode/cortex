# cortex-daemon

The process that keeps one repository's index: the store's only writer, the file watcher, in huge
mode the crawler that parses files in the background, and the miner that reads the git history for
the files that change together. `cortex daemon` runs it.

## What it must never do

- Let anything but its writer write the store, or run twice for one repository: the run folder's
  lock refuses a second daemon, and the store's writer lock refuses a second writer.
- Use the network. It asks git for the user's global gitignore with `git config` alone, which reads
  configuration files and nothing else, and reads the history in-process with `gix`, or with the
  `git` program told never to fetch what a partial clone left out.
- Read the repository's own git configuration for that: a repository could then name the file the
  daemon opens. Nor run a `git` the repository holds: the git it asks is the one the `PATH` names
  outside the repository, in an absolute folder.
- Write code, prompt text or tool output to its log. A line holds the daemon's own words, ids,
  counts, times and paths, at most 1,000 characters on one line.

## Entry points

| Item | What it is |
| --- | --- |
| `run` | Takes the repository's hold first (a lock on `~/.cortex/run/<id>.lock`, released by the system when the process ends, and `<id>.pid` naming the process; a second daemon is refused, naming the first's process), then runs the daemon for a repository's canonical root until it has been idle for `daemon.idle_shutdown_minutes` (no request of any kind, no file change) with nothing waiting to be parsed or recorded; configuration warnings and the ready line go to a callback |
| (miner) | A thread of its own, started once the first index is done, that reads HEAD every 2 s. When a mining is due (nothing mined yet, HEAD moved, or the last full mining a week old), it waits one look, so that the watcher reports the files a checkout wrote, and then until the writer has indexed every change that had come by then; it reads the history for the files the store counts and hands what it found to the writer, which stores it in turns with the hook events recorded between them, and waits for that before it looks again. A look that finds HEAD moved asks for a look at the work tree too, since a commit changes which files are uncommitted without writing one the watcher reports. `gix` reads the history, opened for each read and closed after it, so that no file of the repository stays open between looks (on Windows, git cannot remove a file another process holds open); the `git` program the `PATH` names outside the repository reads it once `gix` cannot open or read the repository, and the status says so with `gix`'s reason. Each look then runs git, so the miner looks every 30 s instead while nothing waits for the index. A failure, a panic in a look among them, is reported, logged and kept among the recent errors; the next try waits 2 s, twice as long after each further failure in a row, at most an hour, or only until HEAD moves when HEAD could be read. A miner that cannot start leaves the daemon running without co-change, its status saying so. Told to stop, it ends at its next look; a read under way ends with the process, and a `git` it was running at its next write to the closed pipe or at its time limit |
| (answers) | A read's hint is followed, in a task, by the line naming the file earlier tasks read next (`cortex_retrieve::next_file`) when there is one, both fit the hint's 120 tokens, the file is claimed for the task under one lock in memory (for the 64 latest, until the writer records the line; given back when the text does not reach the hook), so that two reads answered at once name it once, and then, last, the file is found on disk as indexed (its claim given back when it is not); that line is recorded naming its file, for its use to be counted at the task's end. A store error on that line alone is logged and leaves the read's own hint.  A prompt's request (`Retrieve`), a session start's (`Primer`) and an edit's (`PostEdit`) record their event as an event request does, then are answered on the blocking pool, never on a connection's worker, with the text the agent gets: the work order, silent in tiny mode, before the first index and the graph, when the gate stays shut, and for a held-out task, whose retrieval is recorded all the same; or the primer, or after a compaction the recap of what the session's open task was doing, once for each compaction the agent reported (noted as its `PreCompact` arrives, before the writer records it, and claimed under one lock once there is a recap to give, for the 64 latest sessions; a start after no compaction heard of, as after a restart, counts as one of its own), in every mode and before the first index; or an edit's warnings, worked out in the open task of the edit's session (none outside a task or before the first index): the edited file's symbols whose signature changed, found by reading the file's definitions again and comparing them with the stored ones (only a file the index parsed is read: one whose name matches a secret pattern, too large, binary or generated is never opened), or, when the store already holds the file as it is, from the signature changes the writer's indexes found within the task, kept five minutes (at most 4,096); then what the store says of the file, what the task read, edited and was warned of (stored, and told but not yet recorded: the pairs of each of the latest 64 tasks are kept from the moment they are decided, and the decision is made under one lock, so a pair is told once a task even when two edits are answered at once), and the rules. Warnings are recorded, one row for each file each named, only when their text reached the hook in time: a warning nobody read was not given. A stop's request (`StopReason`) gets nothing unless `strict_mode` is on; then, once a task (claimed under one lock for the 64 latest tasks, once there is a reason), the files that call a signature the task changed and were not read or edited since the warning. A stop is recorded only once its answer is known, and not at all when it was given a reason: the agent goes on, and the task with it, so its edits still count for it and its warnings can still be followed up. A read's request (`ReadHint`), sent the moment before a read, is answered the same way; its event is not recorded, its hint is, as the text given to the session's task: none in tiny mode, before the first index or in a held-out task; else that the session read the lines asked earlier, from the file as it is now, or, in a file over 600 lines, the parts the task's work orders pointed at. A question (`Where`, 1 to 5 files) is answered with what the engine finds without the gate, or with an error, kept among the latest errors, when the engine could not look (a store that cannot be read, a self-check record that is not one). Every retrieval takes the gate's bar as the self-check last raised it, the recent precision it last found and the confidence model kept, when there is one, from the store, and records the model's chance with the injection. What was given or weighed is recorded after its event, once its answer is written, as given to no one (no text hash, no tokens) when the write fails, or when the text was not ready 10 ms before the time the request says its hook stops reading (`answer_by_ms`), in which case it is not sent, or was written after that time; the daemon's latest errors say which. Every text an agent is given is recorded so, at its hook and in its task: the primer, the work order, an edit's warnings (with their rows), a read's hint, a recap and a stop's reason, so that what Cortex added is counted whole. Sessions working at once are coordinated through these same answers: the writer keeps each session's position on each file it read or edited (the one that holds longer, by the `coordination.*` holds); an edit is answered, ahead of its warnings, with a line for each other live session (outside the editing session's parent and subagents) holding the edited file or one linked to it by a reference of confidence 0.8 or more or co-change of 0.5 or more, and a notice is queued for each such session, naming the definitions whose signature the edit changed; a prompt's, an edit's or a read's answer gives the notices waiting for its session first. Each line and notice is given once: claimed under one lock in memory until the writer records it, and queued only when the session was not sent the same text within the edit hold. A held-out task is told none, and its edits still queue notices for the others. A held-out task is given none of them: its work order is worked out and recorded as it would have been, and nothing else is worked out or recorded for it. A reply without text keeps its record, a held-out task's with the hash of what it would have given; a request whose event is of another hook is refused and records nothing. Store readers are pooled, at most four kept; spreading stops 400 ms in |
| (why) | `Why` is answered on the blocking pool from a kept store reader, as `cortex_retrieve::why` works it out, with positions held by the `coordination.*` holds and links of use faded by `learning.link_decay`: the answer as text, or the reason a target names nothing as an error the asker reads; before the first index, that the repository is not indexed yet |
| (upkeep) | The writer's housekeeping, on its own thread, once no hook event has been recorded for 10 minutes and again only after another, at once after a session ends, and as soon as the writer is free after `Consolidate`: links of use faded below 0.01 removed (the graph told), then interest faded below 0.01; the facts reviewed and those retired for 90 days deleted with their anchors; the gate's confidence model fitted when one is due (once 200 injections are labelled, then at most once a day when more are) and kept when it ranks well; events older than 90 days deleted; episodes kept to 50,000, unknown outcomes first; positions that can no longer hold removed; last, `PRAGMA optimize` (reading at most 400 rows of each index) and up to 2,000 free pages given back to the file system, 500 at a time. Each batch of 500 rows is a transaction of its own; a run stops when hook events, a request or a stop wait, carrying on once they are done; after 2 minutes, carrying on at the next quiet spell; or when the write-ahead log holds more than 32 MiB, carrying on 2 s later, by when the checkpointer has copied it, so that upkeep's commits leave the copying to the checkpointer (a reader holding the log, or commits that keep coming, can keep it from starting afresh; each run after a pace then writes one batch and waits again). What it removed is logged and kept for the status |
| (claims) | `Claims` asks to list the claims holding now (from a kept store reader: positions of mode claim still holding by `coordination.claim_minutes`, by file, then session) or to make or release some, which the writer carries out as it does a note: a claim is a position of mode claim from now, held by the session at work (the one whose latest event came last within the 5 minutes before), refused in words when none is or a path is not a file Cortex indexes; a release removes the claims on the files named, whoever holds them, or every claim |
| (work tree) | The files the work tree holds changed against HEAD, or untracked and not ignored (Cortex's own `.cortex` folder left out), read with `git status` on a thread of its own once the first index is done, again after every write the graph is told of and whenever the miner sees HEAD move, at least 2 s apart and at least four times as long after a look as it took; after failures in a row, 4 s after the first, twice as long after each further one, at most 10 minutes. Each file's node is looked up in one read transaction: a file generated, vendored, binary, too large or named like a secret is left out, and of more than 10 the 10 the index saw change last are kept. A diff of more than 5,000 files, or of more than git's 4 MiB listing, is a mass change, none of it kept. Every prompt and every question is seeded with the files kept, as they stand; nothing waits for git. A look that fails is counted, kept among the latest errors and tried again, and no file is kept until a look ends. When the miner sees HEAD move, the files kept are let go at once, and a look already under way is not taken in, so that no file a commit took out of the diff seeds a retrieval past the miner's next look at HEAD, which it takes every 2 s (30 s when the `git` program reads the history) unless a failure, or a mining being written, holds it back. With no git program, no repository at the root, a repository whose own git configuration names a filter (whose command a look would run), or a partial clone with git older than 2.45 (which could fetch what the clone left out), there is nothing to look at and the diff is unknown. The status says how many files are kept to seed retrievals, of how many git listed, and how the looks went |
| (graph) | The graph retrieval spreads over, built once the first index is done and rebuilt whole on a thread of its own after each write that changes it (an index, a stored mining, a task learned from), a rebuild starting at least 0.5 s after the one before however often the store changes, and at least four times as long after it as that one took, so that rebuilding takes at most a quarter of one core. Each rebuild reads the store in one read transaction and is swapped in whole; nothing waits for one, and a stop is taken at once. A rebuild that fails or panics is counted and tried again, a second later after one failure and twice as long after each further one in a row, at most a minute. Co-change links come only from a complete mining: a rebuild that finds the miner's mark out while a mining is being written is let go, the graph standing until the write ends, and one that finds no mark otherwise (nothing mined yet, or a write cut short), or that would be the first graph, builds the graph without them. A huge repository's graph is viewed by files as it is rebuilt, on the rebuild's thread, so that the first stage of its retrievals never waits for that view. The status gives its nodes and links, whether it holds co-change links, how many builds there were and how long the latest took, and how many failed |
| (endpoint) | Bound right after the run lock, before the store opens: on Unix `~/.cortex/run/<id>.sock` at mode 0600 in the 0700 run folder; on Windows the pipe `cortex-<id>`, whose access list allows the current user's identifier alone (read from `whoami`), refusing remote clients. A connection opens with a Hello; another protocol gets a Mismatch and may still send a Shutdown; then Event (queued for the writer; the moment before a tool runs answered only, and a probe from `cortex doctor` answered and counted only), Status (version, protocol, process, uptime, what waits, what was lost, the probes answered, each hook's handling time as percentiles of its last 1,000 requests, the last 10 errors, and what the co-change miner is doing) and Shutdown, which holds even when its acknowledgement cannot be written. A hook's handling time runs from the first byte of its request to its answer being ready; the hook's own process, its connection and the handshake are not in it. At most 64 connections at once; a frame must arrive within 10 s. A connection that breaks (a request that cannot be read, a request before the handshake, a second handshake, an answer that cannot be written) is kept among the recent errors in the daemon's own words, never with the client's bytes, before the client can see the connection end; one closed before a request begins is not an error. An error met again is kept once, with how many times, as the latest |
| (writer) | One inbox feeds the writer: hook events (at most 10,000; when full, a read or search gives way first, and every drop is counted), the watcher's changes, a stop. Events waiting are recorded together in one transaction, all or none; a batch that fails is counted, the store's error is kept among the recent errors, and the daemon goes on. The store opens before the grammars load, and events are recorded every 250 ms while they load and between an index's write transactions, so an event reaches the store within a second whatever the writer is doing. The edits an update of the watcher's changes finds are held 2 s from when the watcher saw them, then recorded after the events waiting (so that a hook's report of the same edit claims it first), for the session most likely to have made them or for none; while an index runs, the recorder knows it, so that a hook's edit recorded in one of its pauses takes nothing from a row it wrote as what the file held before. A task that ends (at the next prompt, or the end of its answer or of its session) is learned from once its batch is stored, each task in a transaction of its own with the events waiting recorded after it: what became of it and why, the interest its work earned, the links between what it used, its record, and, now that it has ended, whether the session's task before it was put back; then the newest task records are clustered again. Fact requests from `cortex note` and `cortex facts` (at most 16 waiting, a further one refused) are taken after the changes waiting, so a note finds the files changed before it indexed, and answered in a transaction of their own: a note's anchors found from their paths and symbol names (`.` the repository's root), the note stated as the user's (active), as an import's from `cortex import` (a candidate, never activated by being imported again), or as an agent's (a candidate) in the open task of the session at work, the one whose latest event came last within the 5 minutes before it; the list; a fact confirmed, retired or corrected by number. One the writer cannot take within 10 s is dropped unwritten and its asker told so; the asker waits 5 s more for the write, and is answered only once the transaction is committed, so what it is told was done is written. The project facts a delivered work order carried are counted as used, and kept as given in its task, once its text reached the agent (written before its hook stopped reading); a held-out task's are not. After every index the facts are reviewed in a transaction of their own: a candidate or active fact whose file or symbol the index found changed or gone turns suspect, and one suspect for 14 days retires; a review that fails is logged and the next index reviews again. Tasks that end while an index or a mining holds the writer wait for it, at most 256, the oldest let go first. The end of an answer, a subagent's stop and a session's end name a transcript, read once their batch is stored, after the tasks waiting are learned from, from where its last read stopped, in passes of the whole lines within 1 MiB (a longer line read whole, as far as 64 MiB), each pass in a transaction of its own with the events waiting recorded after it, and a transcript with more to read waiting again for the next pass: the tokens each response took become usage rows of the event's session (a subagent's own for its stop), numbered by the response's place in the transcript; each row keeps a hash of its response's message id, so that a forked session's copies of its origin's responses count once, for the session that started first; a reading from the transcript's start (its first, or after it was written again shorter than where the last pass stopped) keeps the session's rows as they are until its pass reaches the end, which then removes the rows numbered past the responses the transcript holds, so that the rows are those of the transcript and none is missing meanwhile. A model's name that is not a name (too long, or holding control characters) is stored as no model. A transcript is read only when its path is absolute, its name ends in `.jsonl`, it lies inside a folder its agent keeps transcripts in once every link on the way is followed (for Claude Code `~/.claude/projects`, and the `projects` folder of `CLAUDE_CONFIG_DIR` when the environment the daemon started in sets it to an absolute path), and it is a regular file, opened without following a link; one that is not is logged and kept among the recent errors, in words that name no path. At most 256 transcripts wait, one a path, and 256 have their place kept, the one read longest ago forgotten first; usage the store refuses is counted as a failed batch and its transcript read from its start when an event names it again. However the writer stops (asked to, idle, or on an error once the store is open), it closes the inbox to events, records the events it took and the edits it holds, learns from the tasks waiting and reads the transcripts waiting; an event that arrives after is answered with an error, not acknowledged and lost |
| (log) | `~/.cortex/logs/daemon-<id>.log`, started once the daemon holds the repository: one line per event at info level and above (when it started and stopped and why, the first index, each hook request it handled with the request's id, the hook and the time it took, every error it kept for its status, a failed checkpoint of the store, a panic's location, and the error it stopped on), each line the time in UTC milliseconds, the level, the module, the message and its fields. Errors before the log starts (no home folder, the repository held by another daemon) are the caller's to report. A thread of its own writes the lines from a queue of 1,000, so the daemon never waits for the disk; lines that find the queue full are dropped and counted in the log, and a stopping daemon waits at most 2 s for the rest. Rotated at 10 MiB across five files, as the hook's log is; a log that cannot move aside (on Windows, a reader holding it open) keeps taking lines, and the next try comes after another 10 MiB |
| `Upkeep`, `UpkeepSettings`, `Swept`, `Ended`, `LOG_LIMIT_BYTES`, `PACE_WAIT` | Upkeep's runner as the daemon runs it on its writer, public so that its benchmark runs the same code: a run from where the last stopped, until every job is done, its deadline passes, other work waits or the write-ahead log holds more than its limit, with what it removed and why it ended; after a run that paced, the daemon runs it again `PACE_WAIT` later |
| `is_running` | Whether a daemon holds a repository: its lock on `~/.cortex/run/<id>.lock` is taken (tested by taking it for a moment when free) |
| `settings::load` | The configuration in effect for a repository: the user's `~/.cortex/config.toml`, then the repository's `.cortex/config.toml`, each refused over 1 MiB |

## Tests

```sh
cargo test -p cortex-daemon
cargo test -p cortex-cli --test daemon
cargo test -p cortex-cli --test learning
cargo test -p cortex-cli --test meter
cargo bench -p cortex-daemon --bench upkeep
```

The benchmark builds a large store (20,000 files, 200,000 links of use, 1,000,000 events over
100 days, 60,000 episodes, 10,000 positions, 1,000 facts) and times upkeep on copies of it: a whole
pass through its jobs (the runs, the waits between them left out), and the longest batch of a
pass, the longest a hook event waits behind it. `cargo xtask verify --full` checks both against
their budgets.

The crate's own tests cover the inbox of changes, the run lock, the configuration files, the
global gitignore lookup, and the tasks learned from as they end: before a stop, after an index's
pause and after the edits that fall due, with the events that wait recorded meanwhile, the work
loop woken while tasks wait, and the bound on how many wait; and the transcripts the stops name:
which events name one, the reading rules (links only on Unix, where they need no privileges), a
transcript named twice read once, a transcript longer than a pass read on in the next, usage the
store refuses read again from the start, a transcript written again shorter replacing its rows, one read again after a restart keeping its rows whole, a forked session counting only its own responses whichever transcript is read first, refusals kept as one error, the bounds on the transcripts
waiting and kept, and a stop's transcript read before the daemon stops. The CLI's daemon and server tests
run the real binary on temporary repositories with an empty home folder, including the endpoint's
permissions on each platform; its learning test sends captured Claude Code payloads through
`cortex hook` and reads what two tasks of a session left in the store, its meter test sends a
session's stops with captured transcripts in place and reads the usage rows written, and its
durability test checks that events reach the store within a second while the daemon reads a 24 MiB
transcript of short responses.
