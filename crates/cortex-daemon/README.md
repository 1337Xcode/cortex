# cortex-daemon

The process that keeps one repository's index: the store's only writer, the file watcher, in huge
mode the crawler that parses files in the background, the miner that reads the git history for
the files that change together, and, when it is turned on, the worker that reads which commits
last changed the lines it may show. `cortex daemon` runs it.

## What it must never do

- Let anything but its writer write the store, or run twice for one repository: the run folder's
  lock refuses a second daemon, and the store's writer lock refuses a second writer.
- Serve the user's home folder, a folder holding it, or a file system's root as a repository:
  `run` refuses such a root (`RefusedRoot`) before it records or holds anything.
- Use the network, but for the map it serves to this machine alone: the map listens on 127.0.0.1 only, starts only when asked for its address, answers only requests that carry its token and name it by its own host and origin, and sends no CORS header. It asks git for the user's global gitignore with `git config` alone, which reads
  configuration files and nothing else, and reads the history in-process with `gix`, or with the
  `git` program told never to fetch what a partial clone left out.
- Read the repository's own git configuration for that: a repository could then name the file the
  daemon opens. Nor run a `git` the repository holds: the git it asks is the one the `PATH` names
  outside the repository, in an absolute folder.
- Store or log a commit's message as text, or an author's name: of a commit it stores ids,
  numbers, a kind, node ids, and the words of its subject and reason line split as identifiers
  are, for matching a prompt by; it holds the subject and reason line themselves in memory only,
  and logs none of it.
- Write code, prompt text or tool output to its log. A line holds the daemon's own words, ids,
  counts, times and paths, at most 1,000 characters on one line.

| (miner) | A thread of its own, started once the first index is done, that reads HEAD every 2 s. When a mining is due (nothing mined yet, HEAD moved, or the last full mining a week old), it waits one look, so that the watcher reports the files a checkout wrote, and then until the writer has indexed every change that had come by then; it reads the history for the files the store counts and hands what it found to the writer, which stores it in turns with the hook events recorded between them, and waits for that before it looks again. Each look then runs git, so the miner looks every 30 s instead while nothing waits for the index. A failure, a panic in a look among them, is reported, logged and kept among the recent errors; the next try waits 2 s, twice as long after each further failure in a row, at most an hour, or only until HEAD moves when HEAD could be read. A miner that cannot start leaves the daemon running without co-change, its status saying so. A result whose outcome is unknown (no exit code, interrupted, or a failed shell that printed nothing, which is sent as the event alone) drops the line's earlier run. Notices are not given before a shell command; they come with its result. A stop is recorded only once its answer is known, and not at all when it was given a reason: the agent goes on, and the task with it, so its edits still count for it and its warnings can still be followed up. A read's request (`ReadHint`), sent the moment before a read, is answered the same way; its event is not recorded, its hint is, as the text given to the session's task: none in tiny mode, before the first index or in a held-out task; else that the session read the lines asked earlier, from the file as it is now, or, in a file over 600 lines, the parts the task's work orders pointed at. A contract borne out and within `coordination.max_tokens` is given in its words (`cortex_coord::contract_to_holder`); every other notice names the definitions alone, as the store keeps it. Each line and notice is given once: claimed under one lock in memory until the writer records it, and queued only when the session was not sent the same text within the edit hold. A held-out task is told none, and its edits still queue notices for the others. A held-out task is given none of them: its work order is worked out and recorded as it would have been, and nothing else is worked out or recorded for it. A reply without text keeps its record, a held-out task's with the hash of what it would have given; a request whose event is of another hook is refused and records nothing. | (upkeep) | The writer's housekeeping, on its own thread, once no hook event has been recorded for 10 minutes and again only after another, at once after a session ends, and as soon as the writer is free after `Consolidate`: links of use faded below 0.01 removed (the graph told), then interest faded below 0.01; the facts reviewed and those retired for 90 days deleted with their anchors; the gate's confidence model fitted when one is due (once 200 injections are labelled, then at most once a day when more are) and kept when it ranks well; events and injections older than 90 days deleted, batch after batch while a batch deletes any; episodes kept to 50,000, unknown outcomes first; positions that can no longer hold removed; the blames kept for a file content no indexed file has deleted, and the rest kept to the 50,000 computed last; while the history worker runs, the files worth warming asked of it: the landmarks and the files a session read or edited in the last day that the mined history holds at least 3 commits of, whose content and lines the index read and whose first lines are not kept already and that the worker does not remember as not to blame, at most 32 added to its queue a pass and 200 a UTC day, each from its first line to its 500th at most, in node order, none asked for once the day's are used; last, `PRAGMA optimize` (reading at most 400 rows of each index) and up to 2,000 free pages given back to the file system, 500 at a time. | (history) | A thread of its own, started once the first index is done and only when `history.why` or `history.seeds` is on: with both off there is no thread and no git is run for it. It reads who last changed lines of a file, and what those commits were, for a later prompt to find without running git. While `history.why` is on, a prompt's work order reads the blames and cards kept and the texts held for the spans it lists, asks for at most 4 texts not held, and asks for the blame of each span it shows that has none (never waiting; see `cortex_retrieve::WhyLines`). A blame is asked for by the file's path and the hash of its content as the index read it, and kept under both, so that two files of the same content are blamed apart; a text is read from memory. Both are refused while the thread does not run. The jobs wait in a queue of at most 64, a job asked for again while it waits kept once and the oldest dropped when the queue is full. The thread takes one job at a time and starts no git process while hook events, a request or a stop wait for the writer, while an index or huge mode's crawl is under way or due, or within 300 ms of a hook request arriving; it looks again before every git process of a job, so a request that arrives during a job is waited for between two of them. A span is blamed only when the file on disk still hashes to the hash asked for and is the file at HEAD: the same bytes, or the same once its CRLF line ends are made LF, as git's end-of-line conversion leaves a checkout; one that is not is remembered at that HEAD and not blamed again until HEAD moves. The blame is `git blame` within `history.blame_timeout_ms`, reading no history older than `git.max_age_days` before the daemon's clock; upkeep drops it once its path's file no longer has its content. Each commit it names that has no card is carded, those owning most lines first and at most 16 in a job, the rest left to card jobs of their own, after which the span is looked at once more: its record (`git show -s`), the paths it changed against its first parent as the miner reads a commit, whether it only moved white space (asked only when the card would otherwise be a normal change), the file nodes of those paths that the index holds now and those of them that are tests (by the index's rules for test file paths, or a test found in them), none for a mass change; its symbols are left empty; its terms are the words of its subject and reason line, split as identifiers are. A boundary of the blame is carded only when it is a root. The subject and reason line themselves are neither stored nor logged: they are held in memory for at most 2,000 commits, the one read or put longest ago giving way. When a trivial, mass or bot commit owns lines of the span, the span is blamed once more with each of them ignored (`--ignore-rev`), git mapping their lines through the change to the commits before, and that blame is kept; one step only. A run git blamed on a boundary with a parent (a cut of the history read at the date limit) is not kept; a root commit's is. Next runs of one commit whose lines run on in both files are kept as one. The cards and the blame go to the writer through its queue as one write, in one transaction, and the thread waits for it before its next job. A blame that fails (git does not end in time, say), or that the store refuses, leaves nothing, is counted, and is not run again for that path, content and span while the daemon runs; a commit that cannot be carded, or whose text can no longer be read, is not tried again either (the latest 1,024 of each are remembered). A repository with no git, no repository at the root, a filter in its own git configuration, a partial clone with git older than 2.45 or a blame ignore list other than its top `.git-blame-ignore-revs` is refused for the daemon's life and the status says why. `gix` is opened for each job and closed after it, so that no file of the repository stays open between jobs; the `git` handles are opened again when HEAD's commit changes or a configuration file of the repository (`config` in its shared git folder, `config.worktree` in the working tree's own, a `.git` file followed to them) changes size or modification time. Stopping the daemon waits for the thread at most the longest limit of one of its git processes (`history.blame_timeout_ms`, or 10 s for a commit's record and its white-space check) and a second. The status gives the cards and blames the store keeps, the jobs waiting, the blames that failed and the refusal, if there is one |

## Tests

```sh
cargo test -p cortex-daemon
cargo test -p cortex-daemon history
cargo test -p cortex-daemon map::
cargo test -p cortex-cli --test map
cargo test -p cortex-cli --test daemon
cargo test -p cortex-cli --test why_lines
cargo test -p cortex-cli --test learning
cargo test -p cortex-cli --test meter
cargo bench -p cortex-daemon --bench upkeep
```

The benchmark builds a large store (20,000 files, 200,000 links of use, 1,000,000 events over
100 days, 60,000 episodes, 10,000 positions, 1,000 facts) and times upkeep on copies of it: a whole
pass through its jobs (the runs, the waits between them left out), and the longest batch of a
pass, the longest a hook event waits behind it. `cargo xtask verify --full` checks both against
their budgets.

The crate's own tests cover the inbox of changes, the run lock, the configuration files, the
global gitignore lookup, and the tasks learned from as they end: before a stop, after an index's
pause and after the edits that fall due, with the events that wait recorded meanwhile, the work
loop woken while tasks wait, and the bound on how many wait; and the transcripts the stops name:
which events name one, the reading rules (links only on Unix, where they need no privileges), a
transcript named twice read once, a transcript longer than a pass read on in the next, usage the
store refuses read again from the start, a transcript written again shorter replacing its rows, one read again after a restart keeping its rows whole, a forked session counting only its own responses whichever transcript is read first, refusals kept as one error, the bounds on the transcripts
waiting and kept, and a stop's transcript read before the daemon stops. The history worker's tests run it on repositories made with the `git` program at fixed dates: a
blame of a file whose lines came from a fix, a formatting commit over it that also moved them down a
line, a bot's bump and a mass move is kept with the runs and cards worked out by hand, the
formatting commit and the move looked through; a card's row holds no word a person wrote; a blame
past its time leaves nothing and is not run again; a file with CRLF line ends on disk and LF in the
commit is blamed under the disk's hash, an uncommitted edit, a line count kept or not, gets no blame
until it is committed; two files of the same content written by different commits are blamed apart;
a commit left past a job's cards is looked through on the span's second look; a repository whose
configuration names a filter is refused; nothing starts with both switches off; and upkeep warms the
files it should and prunes and caps the blames kept. The queue's bound and order, the text cache's
bound and order, the memories' bounds, which owners are looked through, the line-end comparison and
the rule that keeps git away from hooks and the index have tests of their own. The CLI's why-lines
test runs the real binary with `history.why` on: a prompt's work order gets the fix's why-line once
the blame is kept, and an edit of the line the fix wrote, its event sent once the watcher has
indexed the edited file, gets the origin note. The CLI's daemon and server tests
run the real binary on temporary repositories with an empty home folder, including the endpoint's
permissions on each platform; its learning test sends captured Claude Code payloads through
`cortex hook` and reads what two tasks of a session left in the store, its meter test sends a
session's stops with captured transcripts in place and reads the usage rows written, and its
durability test checks that events reach the store within a second while the daemon reads a 24 MiB
transcript of short responses.
